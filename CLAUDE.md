# Media Dashboard — 103 ОБр ТрО, відділення комунікацій

## Що це

Дашборд для обліку медіа-активності відділення комунікацій бригади: ефіри,
події, інфоприводи, рекламні кампанії, контакти журналістів і військових,
моніторинг ворожих згадок, статистика соцмереж, конвеєр відеозйомки/фотозйомки.
Інтерфейс повністю українською — усі тексти, назви полів, повідомлення
користувачу мають лишатися українською.

## Старт нової сесії (почни звідси)

Користувач — не програміст, спілкується українською, хоче бачити результат, а не міркування.
У хмарній сесії папка проєкту на старті **порожня** — репозиторій треба підключити:
1. `list_repos` → знайти `103tro/Media-dashboard-for-communication-department`;
   `add_repo` (з `access: "push"`) → `git clone --depth 1 <url> /home/user/media-dashboard-for-communication-department`
   (великий тайм-аут, один клон) → `register_repo_root`. Після цього цей файл підвантажується сам.
2. `cd tests && npm install` (один раз за сесію) — тести потрібні для кожної зміни.
3. Нова функція — спершу коротко погодити дизайн у чаті (що зміниться, які файли, як перевіримо) і
   дочекатись «так». Дрібне виправлення — просто робити.
4. Порядок роботи: **тест, який падає → реалізація → `npm test` → перевірка форми в Chromium
   (знімок екрана) → коміт → PR → merge → пояснити користувачу простими словами, що змінилось.**
5. Попереджати, якщо щось займає довго (інсталяція, повний прогін тестів ~1–2 хв), — користувач не бачить, що відбувається.

## Самооновлення цього файлу

Цей файл — єдина пам'ять проєкту, що переживає будь-яку кількість нових
чатів. Тому: якщо під час роботи виникає нова стала домовленість чи
конвенція (не одноразове прохання, а правило типу "відтепер завжди робимо
так") — одразу дописуй її коротким рядком у "Журнал домовленостей" нижче
(з датою) і, якщо вона стосується архітектури/процесу, заведи під неї
окремий розділ вище. Роби це сам, без нагадування користувача — саме для
цього файл існує.

## Архітектура

- **Один файл**: `index.html` (понад 8000 рядків, зростає) — вся логіка, стилі й розмітка.
  Без збірки, без бекенду, без npm-залежностей у самому проєкті.
- **Зовнішні бібліотеки** підключені прямо з CDN у `<head>`:
  Chart.js 4.4.1 (`cdnjs.cloudflare.com`), xlsx 0.20.3 (`cdn.sheetjs.com`, з
  fallback на cdnjs 0.18.5, якщо CDN недоступний), pptxgenjs 3.12.0
  (`cdn.jsdelivr.net`). Нових бібліотек так само додавати через CDN-тег, не
  через збірку.
- **Дані живуть у браузері**: увесь стан — об'єкт `DB` (broadcasts, contacts,
  militaryContacts, enemyMentions, shoots, соцмережі, групи каналів,
  підрозділи тощо), серіалізований у `localStorage` під ключем
  `media_dashboard_v1` (`loadDB()` / `saveDB()`). Немає сервера — дані не
  синхронізуються між користувачами й пристроями автоматично. Єдиний спосіб
  перенести дані — експорт/імпорт JSON-бекапу через UI.
- **Код — глобальний**: усі функції оголошені як `function name(){}` на
  верхньому рівні (хостяться), стан — у top-level `let`/`const`. Немає
  модулів, немає класів для UI-логіки.
- **Рендер по вкладках**: `setTab(id)` перемикає вкладку, кожна вкладка має
  свою `renderX()`-функцію (`renderOverview`, `renderBroadcasts`,
  `renderContacts`, `renderMilitaryContacts`, `renderEnemyMentions`,
  `renderSocial`, `renderShoots`, ...), яка повністю перемальовує свою
  панель із поточного `DB`. Зміна даних → виклик відповідного `renderX()`,
  а не ручне патчення DOM.

## Кастомні теми ("Персоналізація")

Кольори керуються CSS-змінними (`--ink`, `--surface`, `--brass`, `--navy`,
...). Важливі нюанси, на яких уже були баги:
- `--surface` (фон картки) НЕ кастомізується користувачем, на відміну від
  `--ink`-сімейства — тому текст на картках/панелях має йти через
  `--ink-on-surface*`, а не напряму через `--ink`.
- Текст на кастомному фоні (сайдбар, акцентні кнопки) обчислюється через
  `pickTextColor(hex)` (авто-контраст за яскравістю), а не хардкодиться
  білим/чорним.
- Графіки (Chart.js/SVG) не бачать CSS-змінних напряму — колір береться
  через `liveAccentColor()` (`getComputedStyle`), а не хардкодженим hex.
- Будь-який новий кольоровий UI-елемент має пройти перевірку: що буде при
  дуже світлій і дуже темній кастомній палітрі, а не тільки за замовчуванням.

## Git-процес

- Кожна задача — **нова гілка від свіжого `origin/main`** з назвою `claude/<суть-задачі>`
  (стара довга гілка `claude/compassionate-fermi-xskxrx` більше не використовується).
- Публікація йде через GitHub Pages з `main` — отже, зміна "живе" для
  користувача лише після merge у `main`, не після push у робочу гілку.
- Процес для кожної зміни: branch → commit (описове повідомлення, що й чому)
  → push → Pull Request → merge у `main`. Жодна зміна не вважається
  завершеною без merge. Merge у `main` публікує сайт, тож робиться за явним
  словом користувача («публікуй», «зливай», «сам роби»); без нього — PR і запитати.
- **GitHub із хмарної сесії** (перевірено 2026-11-02):
  - `gh pr create` не працює (GraphQL заблоковано) — створювати PR через REST:
    `gh api repos/103tro/media-dashboard-for-communication-department/pulls --method POST --input pr.json`
    (JSON із `title`, `head`, `base`, `body`; файл класти в scratchpad, не в репозиторій).
  - Merge: `gh api repos/103tro/media-dashboard-for-communication-department/pulls/N/merge --method PUT -f merge_method=merge`.
    Автоматична перевірка дозволів може відмовити в merge, доки користувач явно не скаже «роби» —
    тоді не обходити, а зупинитись і спитати.
  - Статус збірки Pages з сесії не видно (проксі не пускає) — просто сказати користувачу оновити сторінку
    з очищенням кешу (Ctrl+Shift+R) за 1–2 хвилини.
  - Хук «є непушені коміти» після успішного push — це неглибокий клон без посилання `origin/<гілка>`:
    `git fetch origin <гілка>:refs/remotes/origin/<гілка>`.
  - Клон неглибокий (`--depth 1`); перед push `git fetch origin main`, щоб не слати зайвого.

## Безпека та цілісність даних

Правила, які з'явились після аудиту (2026-11-01); порушувати не можна:
- **Посилання в `href`** — лише через `safeHref()` / `safeUrl()` (дозволені
  `http(s)`, `mailto`, `tel`). Значення в атрибутах — через `attr()`, текст — через
  `esc()`, колір, що прийшов із даних, — через `safeColor()`. Дані з бекапу чи Excel
  не можна вважати довіреними.
- **Дати** — календарну дату ніколи не брати як `toISOString().slice(0,10)` (це UTC,
  у Києві зсуває день): `localISO()` / `todayISO()`. Дати з Excel читаються з
  серійного номера через `XLSX.SSF` (`cellNF:true`), а не через `cellDates`.
- **Запис у `localStorage` — лише через `saveDB()`.** Він не перезаписує нерозпізнане
  сховище (`storageLocked`) і не пише із застарілої вкладки (`lastSeenRaw`).
- Імпорт бекапу спершу завантажує `before-import-ДАТА.json` зі старими даними та
  перевіряє форму файлу (`validateBackupShape`).
- Імена, позивні, підрозділи, телефони не зашиваються в код (ні в `migrate()`, ні в
  сід): `migrate()` лише приводить структуру до поточної, а не лагодить дані
  конкретних людей, бо виконується при кожному завантаженні.

## Помилки та повторювані шматки коду

- Збій, про який користувач має знати, показується через `reportError(текст, err)` (довгий
  тост + деталі в консоль); асинхронну дію, що може впасти (звіт, імпорт), викликати через
  `guarded(текст, fn)`. Мовчазних `catch` не лишати. Останній рубіж — глобальні
  `error`/`unhandledrejection` (`reportUnexpected`, не частіше за раз на 5 с).
- Підписка на події розбита на `wireXxxEvents()` за вкладками/вікнами; `wireEvents()` лише
  викликає їх по черзі. Нова кнопка/вікно — у функцію своєї вкладки, а не в одну довгу.
- Посилання-або-текст — `extLink(url, text)`, порожній стан — `emptyStateHtml(text)`;
  обидва самі екранують, тож у місцях виклику `esc()`/`safeHref()` повторювати не треба.

## Тестування

- **Автоматичні перевірки лежать у `tests/`** (`cd tests && npm install && npm test`, ~20 с).
  Десятки перевірок (актуальна кількість — у кінці виводу `npm test`; цифри в журналі нижче —
  знімки на свою дату) у справжньому Chromium за часовим поясом `Europe/Kyiv`: запуск усіх 9 вкладок,
  збереження, міграція старого формату, зіпсоване сховище, дві вкладки, імпорт бекапу
  (`before-import-*.json`), ворожі дані (XSS), дати, створення запису через форму.
  `tests/` має власний `package.json` і не входить у сайт; сам `index.html` лишається без npm.
  **Перед кожним PR у `main` запускати `npm test`; якщо правка зачепила збереження, міграцію,
  імпорт, дати чи рендер із даних — спершу додати/оновити відповідну перевірку.** Нова вкладка
  чи новий тип запису = додати його в сценарій "ворожих даних" (розділ 7 у `tests/run.js`).
  Перевірки вже довели, що вміють падати (навмисно ламали `safeUrl`, `localISO`, захист від
  застарілої вкладки та блокування зіпсованого сховища — кожну поломку було виявлено).
  У пісочниці `xlsx` для тестів береться 0.18.5 з npm, бо `cdn.sheetjs.com` недоступний.
- Пісочниця блокує вихід на `cdnjs.cloudflare.com` / `cdn.jsdelivr.net`,
  тож пряме відкриття `index.html` у Playwright не підвантажує Chart.js
  та інші CDN-бібліотеки.
- Перевіряти зміни так: `npm install chart.js@4.4.1` (або `xlsx`,
  `pptxgenjs`, за потреби) у тимчасову директорію (не в корінь проєкту), тоді
  в Playwright підмінити CDN-запит реальним локальним бандлом через
  `page.route('**/chart.umd.js**', route => route.fulfill({...}))` —
  і вже на цьому прогнати реальний сценарій (синтетичні дані в `DB`,
  клік по вкладках, перевірка чисел/підписів), а не просто читати код.
- Дати й часові пояси перевіряти з `browser.newContext({timezoneId:'Europe/Kyiv'})` —
  у UTC помилки зсуву дати не видно. Для тестів із двома вкладками сторінку віддавати
  через `python3 -m http.server`, а не `file://`.
- У `page.evaluate()` top-level `let`/`const` зі скрипта сторінки доступні як
  "голі" ідентифікатори (`monthlyChart`, не `window.monthlyChart`) — вони не
  висять на `window`.

## Карта коду (шукай за назвою функції, не за номером рядка — рядки пливуть)

- **Дані**: `SEED_DATA` (початкові дані), `let DB`, `loadDB()` / `saveDB()`, `migrate(db)`,
  `validateBackupShape()` (імпорт бекапу). Нове поле в `DB` = додати в `migrate()` (лише структуру,
  без даних конкретних людей) і в `validateBackupShape()`, якщо воно обов'язкове.
- **Вкладки** (`setTab(id)`): overview, broadcasts, crosstab, contacts, military, enemy, social,
  shoots, settings; кожна має `renderX()`, а її кнопки/вікна підписує `wireXxxEvents()`.
- **Ефіри й події**: форма — `openBroadcastModal(id)` / `saveBroadcast()` / `closeBroadcastModal()`;
  розмітка вікна — `id="broadcastModal"` (поля `f_*`); тип запису (`b.type`): «ефір» (прямий ефір радіо/ТБ),
  «інтерв'ю» (текстове, з військовослужбовцем), «стаття» (загальна згадка), «подія», «реклама»
  (`classifyType`, `EVENT_CHANNELS`). Перелік типів — `RECORD_TYPES` (назви, колір, чи показувати порожнім):
  з нього будуються картки Огляду, місячний/річний графіки (`visibleTypeSeries`, `typeListPhrase`) і звіт pptx;
  `<select id="f_type">` у формі та `<select id="filterType">` у списку — звичайна розмітка, їх міняти вручну.
  Новий тип = рядок у `RECORD_TYPES` + опції у двох select + розділ 12 тестів. Після збереження перемальовуються `renderNav`, `renderBroadcasts`,
  `renderOverview`, `renderCrosstab`.
- **Групи каналів**: `DB.channelGroups` = `{ "назва каналу малими літерами": "Назва групи" }`
  (ключ — `normalizeChannelKey()`); `channelGroupOf(канал)` повертає групу або сам канал, якщо групи
  немає; вікно «Групи каналів» — `openChannelGroupsModal` / `saveChannelGroups` / `allChannelStats`;
  у формі запису — `applyChannelGroup`, `syncChannelGroupField`; групування в статистиці —
  `buildChannelGroupIndex` (кросс-таблиця) та місця, що викликають `channelGroupOf`. У вікні груп
  «групою» вважається лише те, де каналів більше одного, решта йде в блок «Без групи».
- **Підказки при введенні**: `wireMultiNameAutocomplete` (поле + власний список), `wireDelegatedAutocomplete`
  (рядки, що перемальовуються), `wireEventPicker` (вибір події за id). Нове поле з підказкою — через них.
- **Повідомлення**: `showToast` (звичайне), `reportError` / `guarded` (збої).

## Чого Claude не бачить і як із цим жити

- Реальні дані користувача (його групи каналів, записи, контакти) лежать у `localStorage` **його браузера**.
  Репозиторій містить лише `SEED_DATA` і код. Не вгадувати, які в нього групи/канали: якщо від цього
  залежить рішення — спитати, або попросити свіжий JSON-бекап (кнопка експорту в інтерфейсі).
- Нічого, що користувач внесе в інтерфейсі, не потрапляє в репозиторій і не бачиться з сесії.
  Зміна коду не змінює його наявних даних — нові поля мають працювати зі старими записами без міграції даних.
- Користувач не бачить, що відбувається в сесії, поки не отримає відповідь: перед довгими кроками
  попереджати, а підсумок писати простими словами (що змінилось у дашборді, як цим користуватись,
  що лишилось ним зробити).

## Пастки тестів (щоб не губити час)

- `innerText` не читає значення полів вводу — для `<input>` брати `inputValue()`.
- Якщо локатор не знайдено, Playwright чекає 30 с на кожну перевірку — нові перевірки спершу гнати на
  вузькому наборі або розуміти, що «червоний» етап буде повільним.
- Візуальна перевірка форми: невеликий скрипт Playwright із підміною CDN (як у `tests/run.js`:
  `CDN_MAP`), знімок екрана зберегти в scratchpad і переглянути; у репозиторій знімки не класти.
